# Day 3：MCP 与 Function Calling

## Q1：MCP 和 Function Calling 的区别？
Function Calling 是**模型侧**的基础调用机制：模型根据 tools 定义决定调用哪个、填什么参数。
MCP 是**应用侧**的工具接入协议：定义 Server 如何暴露能力（Tools/Resources/Prompts）、Client 如何发现和调用。
两者不是替代关系：MCP Server 暴露的 Tools，最终仍以 Function Calling 的形式交给模型。
边界：MCP 只解决标准连接与能力表达，不自动解决业务正确性和企业安全。

## Q2：MCP Server 暴露什么？
三类能力：
- Tools（动词）：可被调用的动作，只读或有副作用
- Resources（名词）：用 URI 标识的只读数据
- Prompts（模板）：预定义提示词模板
不是“普通 HTTP API 的简单包装”：它要求标准的能力描述（name/description/inputSchema）、
治理元数据、以及客户端可发现性。生产还要权限、幂等、超时、结果大小限制、多租户隔离。

## Q3：为什么用 MCP 而不是继续只用 Function Calling？
因为要让多个客户端（Claude Desktop、Cursor、自研 Agent）用同一套标准发现并调用同一批能力，
避免每个客户端各写一套接入。
失效条件：单工具、单客户端场景，MCP 引入额外协议层，反而增加复杂度。

## Q4：工具发现后为什么还要 Registry 过滤？
发现是客观事实（Server 上有什么），投影是准入决定（哪些允许模型看见）。
缺治理元数据的裸工具能被调用但无法被治理；Registry 过滤是投影前的第二道闸。
失效条件：单身份单租户演示可简化；企业不能省。

## Q5：stdio 和 Streamable HTTP 怎么选？
- 本地开发、单机演示：stdio（Client 拉起子进程，零网络配置）
- 需要多进程共享同一 Server、远程多租户、企业接入：Streamable HTTP + 认证授权
失效条件：远程多租户还走 stdio，别人连不进来；Streamable HTTP 不加认证，等于裸奔。

## Day 5：Agent 答错了，是选错工具还是用错返回结果？

我不会笼统说“Agent 不好用”，而是用结构化执行日志做四层归因。

**第一，先看日志有没有证据。**  
每次任务执行有唯一 `trace_id`，每一步记录 `tool、params、result、elapsed_ms、error_type、is_retry、is_approval`。  
按 `trace_id` 回放，就能看到错误发生在第几步、调了什么工具、传了什么参数、返回了什么。

**第二，把错误拆成四层。**  
- 工具选择层：选错工具，或该选未选；  
- 参数生成层：缺参、类型错、枚举越界；  
- 工具返回层：超时、429、5xx、空返回；  
- 忽略返回层：工具已返回可用结果，但模型没采用。

**第三，用数字说话。**  
以 6 条 badcase 为例，统一分母 N=6，逐层命中独立统计：  
工具选择错误率 33.3%，参数生成错误率 33.3%，工具返回异常率 16.7%，忽略返回错误率 16.7%。  
一条 badcase 可多层命中，所以四层错误率相加可能超过 100%。

**第四，主层看治理。**  
命中层用来算比率，主层取“修复后最能消除这条 badcase 的那一层”。  
比如参数越界导致下游空返回、模型又忽略空返回，主层定参数生成，因为修好 Schema 校验最能消除错误。

**最后说治理动作。**  
工具选择错误 → Registry 过滤 + 工具选择评测；  
参数错误 → JSON Schema 校验 + 结构化回传；  
工具返回异常 → Timeout/Retry/Fallback/熔断；  
忽略返回 → 结果校验 + 后置验证 + 截断摘要。

所以回答是：**先按 trace_id 回放拿证据，再做四层标注算错误率，最后看修复哪一层最能消错，就定位到是选错工具还是用错结果。**

### Q: 你的 Agent 治理层到底带来了什么量化收益？有没有代价？
**A:** 
我通过“裸 ReAct”和“治理后 Agent”在相同任务集和故障注入下的对比实验，得出了明确的量化收益：

1. **极大提升了任务高可用（核心收益）**：在注入超时、429、5xx 等故障场景下，裸版的完成率仅有 **10%**，超时恢复率为 **0**，遇到异常直接卡死；而治理版的完成率达到 **100%**，超时恢复率 **100%**。治理层通过重试和降级兜底，保住了任务的最终交付。
2. **写操作安全边界（防重大事故）**：在写操作（如转账、下单）超时的致命场景下，裸版会盲目重试或卡死，极易导致“重复扣款”；治理版能精准识别写操作属性，走 `DEGRADED` 降级路径（停止盲目重试，转为查证/提示），杜绝了副作用灾难。
3. **治理的代价（Trade-off）**：天下没有免费的午餐，治理层带来了平均步数从 **1.2** 增加到 **1.9**，以及在简单任务上约 **+50%** 的额外延迟。
4. **失效条件（何时关闭）**：当任务是“简单单工具读操作”（如查天气），且延迟极其敏感时，重试和降级保护带来的收益抵不过延迟开销。在这种极端场景下，允许关闭部分重治理模块，仅保留轻量日志。
